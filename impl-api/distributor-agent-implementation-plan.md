# 新增经销商 Agent 分步骤实现大纲

## 1. 文档目标

本文档用于定义“新增经销商 Agent”的分步骤实现计划。

目标：

- 将整体实现拆成多个可独立推进的阶段
- 每一步明确要做什么
- 每一步明确完成后应达到的效果
- 每一步明确应补充哪些测试以及预期结果

本文档面向工程实施，不重复展开完整设计细节，设计依据参考：

- [distributor-agent-design.md](/Users/ganzhiwen/workspace/InformationEntryAgent/impl-api/distributor-agent-design.md)

## 2. 实施原则

- 先搭骨架，再补能力
- 先把状态和流程跑通，再优化抽取质量
- 先用 mock 校验和 mock 创建接口打通主链路
- 每一步都要求可运行、可测试、可验证
- 不在 V1 初期引入不必要的复杂度

## 3. 分阶段总览

建议按以下顺序推进：

1. 项目骨架与基础模型
2. 会话状态与必填规则
3. 规则抽取器
4. LLM 增量抽取器
5. 字段合并与修改覆盖
6. mock 校验服务
7. 对话决策与文本回复
8. FastAPI 接口层
9. 汇总确认与 mock 创建
10. Redis 会话存储
11. 端到端联调测试
12. 性能优化与质量收尾

## 4. 详细步骤

### Step 1. 项目骨架与基础模型

#### 要做什么

- 创建 `app/agent` 和 `app/api` 基础目录
- 创建基础模块文件
- 定义 Pydantic 数据模型：
  - `MainInfo`
  - `Contact`
  - `Site`
  - `ValidationResult`
  - `SessionState`
  - `ChatRequest`
  - `ChatResponse`
- 定义枚举或常量：
  - `stage`
  - `status`
  - 必填字段路径常量

#### 达到的效果

- 代码结构成型
- 后续逻辑不再依赖松散字典
- 状态和请求响应结构统一

#### 完成后的测试结果

- 能成功导入全部模型类
- 基础模型可以正确序列化和反序列化
- 非法枚举值会触发模型校验失败

#### 建议测试

- `tests/test_models.py`
- 预期：
  - 合法 `SessionState` 创建成功
  - 非法 `status` 值报错
  - 联系人缺少字段时模型层按预期处理

### Step 2. 会话状态与必填规则

#### 要做什么

- 实现状态初始化逻辑
- 实现 `compute_missing_fields(state)`
- 实现联系人有效性判断
- 实现条件必填逻辑：
  - `distributorLevel == 2` 时要求 `parentDistributorName`
- 实现默认值逻辑：
  - `distributorLevel` 默认 `1`
  - `providePoints == false` 时 `providePointsRatio = 0`

#### 达到的效果

- 系统能在不依赖模型的情况下判断当前还缺什么
- 缺失字段判断有统一、稳定的规则出口

#### 完成后的测试结果

- 空白会话能返回正确缺失字段列表
- 填入部分字段后缺失项正确减少
- 二级经销商缺少上级名称时能正确识别
- 联系人不完整时能识别联系人字段缺失

#### 建议测试

- `tests/test_required_rules.py`
- 预期：
  - 默认 `distributorLevel=1`
  - `providePoints=false` 时比例自动归零
  - 完整联系人满足联系人必填规则

### Step 3. 规则抽取器

#### 要做什么

- 实现纯规则提取模块
- 优先支持以下字段提取：
  - 手机号
  - 邮箱
  - ERP 编码
  - 日期
  - 折扣
  - `providePoints`
  - `providePointsRatio`
  - `status`
  - “微信同手机号”
- 支持基础联系人规则提取
- 输出统一 patch 结构

#### 达到的效果

- 对格式明显的字段，无需调用 LLM 即可提取
- 降低后续模型调用压力

#### 完成后的测试结果

- 给定固定文本，规则抽取结果稳定可重复
- 折扣、日期、布尔值可以正确归一化
- 联系人微信同手机号能转成 `same_as_mobile`

#### 建议测试

- `tests/test_rule_extractor.py`
- 预期：
  - `58折` -> `0.58`
  - `发积分` -> `true`
  - `不发积分` -> `false`
  - `2026年6月1日` -> `2026-06-01`

### Step 4. LLM 增量抽取器

#### 要做什么

- 实现 LLM 抽取入口
- 只处理本轮用户输入，不处理全量历史对话
- 输入上下文包括：
  - 当前结构化状态摘要
  - 当前缺失字段
  - 本轮用户输入
- 重点支持以下语义字段：
  - `distributorName`
  - `belongRegion`
  - `mainCategory`
  - `mainCategoryGrade`
  - `businessType`
  - `cooperationStatus`
  - 联系人职位与关系
  - 修改意图识别
- 输出 patch 结构并做基础格式兜底

#### 达到的效果

- 系统可以识别复杂语义字段
- 系统具备多轮补充和字段修改能力

#### 完成后的测试结果

- 给定稳定样例，LLM 输出可被正确解析
- 用户表达修改时，能输出覆盖型 patch
- 用户补充新联系人时，能输出新增型 patch

#### 建议测试

- `tests/test_llm_extractor.py`
- 预期：
  - 模型输出结构符合 JSON 约定
  - 模拟“手机号改成 xxx”时返回变更 patch
  - 模拟“老板叫王磊”时联系人字段正确落位

### Step 5. 字段合并与修改覆盖

#### 要做什么

- 实现 `merge_state(state, patch)`
- 主信息采用字段级覆盖
- 联系人按以下优先级匹配并更新：
  - `contactName`
  - `position`
  - 无法唯一匹配时新增或返回待澄清标记
- 场地按 `siteType + fullAddress` 合并
- 记录 `field_meta`

#### 达到的效果

- 多轮输入可以累计成完整状态
- 用户修改已有字段时能正确覆盖，而不是重复堆积

#### 完成后的测试结果

- 多轮补充后状态逐步变完整
- 同一个联系人多次补充不会生成重复联系人
- 修改手机号后旧值被覆盖

#### 建议测试

- `tests/test_state_merge.py`
- 预期：
  - 联系人二次补充合并成功
  - 主信息同字段重复输入时取最新值
  - `field_meta` 正确记录来源轮次

### Step 6. mock 校验服务

#### 要做什么

- 定义 `ValidationService` 抽象
- 实现 mock 名称校验
- 实现 mock 手机号校验
- 实现 mock 邮箱校验
- 设计校验结果缓存和重校验触发机制

#### 达到的效果

- 强校验字段具备统一校验入口
- 为后续切换真实后端接口保留稳定边界

#### 完成后的测试结果

- 合法名称、手机号、邮箱返回通过
- 非法手机号、邮箱返回失败
- 修改字段后能触发重新校验

#### 建议测试

- `tests/test_validators.py`
- 预期：
  - `13800138000` 通过
  - `123456` 失败
  - `a@b.com` 通过
  - 非法邮箱失败

### Step 7. 对话决策与文本回复

#### 要做什么

- 实现 `decide_next_action(state)`
- 实现 `render_reply(state, action)`
- 支持以下动作：
  - 追问缺失字段
  - 提示校验失败
  - 展示汇总
  - 等待确认
  - 返回创建结果
- 每轮最多追问 1 到 2 个关键字段

#### 达到的效果

- Agent 从“只会提字段”升级到“会推进流程”
- 用户收到的是可直接交互的自然语言回复

#### 完成后的测试结果

- 缺字段时会追问正确字段
- 字段非法时优先提示修正
- 全部完成后进入确认阶段

#### 建议测试

- `tests/test_dialog_policy.py`
- 预期：
  - 缺邮箱时回复中包含邮箱追问
  - 手机无效时回复中包含修正提示
  - 全部满足时 action 为 `awaiting_confirmation`

### Step 8. FastAPI 接口层

#### 要做什么

- 创建 FastAPI 应用入口
- 提供基础 chat 接口：
  - `POST /api/agent/distributors/chat`
- 请求体至少包含：
  - `session_id`
  - `message`
- 响应体至少包含：
  - `reply`
  - `stage`
  - `missing_required_fields`
  - `validation_results`
  - `state_summary`
- 提供健康检查接口

#### 达到的效果

- 前端可以直接通过 HTTP 进行多轮会话联调
- Agent 不再是纯本地函数，而是可运行服务

#### 完成后的测试结果

- 健康检查接口正常返回
- chat 接口可接收输入并返回结构化响应
- 非法请求体会得到正确错误码

#### 建议测试

- `tests/test_api_chat.py`
- 预期：
  - `200 OK`
  - 返回 `reply`
  - 缺少 `session_id` 或 `message` 时返回 `422`

### Step 9. 汇总确认与 mock 创建

#### 要做什么

- 定义确认创建逻辑
- 设计用户确认识别：
  - “确认创建”
  - “可以，创建吧”
  - “没问题，提交”
- 实现 mock 创建服务
- 创建前再次检查：
  - 必填完整
  - 强校验通过
  - 当前阶段合法

#### 达到的效果

- 主链路可以完整闭环
- 从“收集信息”走到“创建成功”具备可演示能力

#### 完成后的测试结果

- 未完成字段时确认创建会被拦截
- 满足条件后确认创建会成功
- 创建成功后状态进入 `completed`

#### 建议测试

- `tests/test_create_flow.py`
- 预期：
  - 条件不足时返回不可创建
  - 条件满足时返回创建成功响应

### Step 10. Redis 会话存储

#### 要做什么

- 抽象 `SessionStore`
- 提供内存版实现
- 提供 Redis 版实现
- chat 接口改为从存储层读取和写回状态
- 支持会话 TTL

#### 达到的效果

- 会话状态不依赖单进程内存
- 服务具备多实例扩展基础

#### 完成后的测试结果

- 同一 `session_id` 多轮调用可以恢复之前状态
- 不同 `session_id` 状态隔离
- Redis 不可用时能明确报错或回退

#### 建议测试

- `tests/test_session_store.py`
- 预期：
  - 写入后可读取
  - 会话隔离正确
  - TTL 生效逻辑正确

### Step 11. 端到端联调测试

#### 要做什么

- 编写完整多轮对话用例
- 覆盖以下典型场景：
  - 一次性提供大量信息
  - 多轮逐步补充
  - 中途修改字段
  - 校验失败后修正
  - 二级经销商强制要求上级名称
- 验证最终能走到确认和创建

#### 达到的效果

- 核心主流程具备稳定回归保障
- 真实交互路径已经可验证

#### 完成后的测试结果

- 全部端到端样例通过
- 多轮状态变化符合预期
- 每轮回复能够推动流程前进

#### 建议测试

- `tests/test_e2e_conversation.py`
- 预期：
  - 至少 3 到 5 组完整会话样例全部通过

### Step 12. 性能优化与质量收尾

#### 要做什么

- 检查每轮处理耗时
- 减少不必要的 LLM 调用
- 优化 prompt 长度
- 增加日志和调试信息
- 补充异常处理
- 清理接口返回结构

#### 达到的效果

- 响应速度进入可交互范围
- 错误可定位
- 代码具备后续接真实接口的可维护性

#### 完成后的测试结果

- 普通规则型输入无需调用 LLM 时响应明显更快
- LLM 抽取失败时服务不会崩溃
- 错误日志可定位到阶段、字段和会话

#### 建议测试

- `tests/test_error_handling.py`
- `tests/test_performance_smoke.py`
- 预期：
  - 抽取异常时能返回兜底回复
  - 基础 smoke 测试通过

## 5. 建议先后优先级

建议第一批先完成：

1. Step 1
2. Step 2
3. Step 3
4. Step 5
5. Step 6
6. Step 7
7. Step 8

完成这一批后，就已经有一个：

- 可运行
- 可对话
- 可追问
- 可校验
- 可查看缺失字段

的最小可用版本。

第二批再完成：

1. Step 4
2. Step 9
3. Step 10
4. Step 11
5. Step 12

这样做的原因是：

- 先跑通主链路
- 再提升抽取质量
- 再补部署级能力

## 6. 每一步的验收标准

每个阶段结束时都建议满足以下验收要求：

- 有对应代码提交
- 有至少一个对应测试文件
- 测试可以运行
- 有明确的输入输出示例
- 不破坏前一阶段已有能力

## 7. 推荐执行节奏

实际开发建议按以下节奏推进：

1. 先完成 Step 1 到 Step 3
2. 立即跑第一轮单元测试
3. 再完成 Step 5 到 Step 8
4. 做一次本地接口联调
5. 再补 Step 4 和 Step 9
6. 最后接 Redis 和做端到端测试

## 8. 结论

这份分步骤计划的目标不是把所有能力一次堆完，而是保证每一步都能落地、能验证、能继续迭代。

推荐的实现策略是：

- 第一阶段先做最小可用链路
- 第二阶段补 LLM 增量语义抽取
- 第三阶段补会话存储、端到端联调和性能优化

只要严格按这个顺序推进，后续接真实校验接口和新增经销商接口时改动会最小。
